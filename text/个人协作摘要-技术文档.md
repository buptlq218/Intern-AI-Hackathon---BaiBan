# 个人协作摘要 —— 技术文档

> 功能标识：`summarize_personal_collaboration` 代码基线：`ncode-pilot-runtime` / `master` @ `39edf61b`；`nc-pilot-web` / `master` @ `40ed9d0` 状态：已上线

---

## 1. 功能定位

`summarize_personal_collaboration` 是恩熙在**用户与恩熙的 1v1 私聊**中提供的"个人协作待办汇总"只读工具。

它解决的问题是：用户不必逐个进入自己可见的项目群，即可一次了解近期需要关注的协作事项，并进入完整摘要面板继续处理。典型提问是"我有什么待办事项""最近有哪些需要我关注""有没有 @ 我的事项"。

**输入范围是当前用户可见的数字人群聊项目看板**，不是钉钉个人待办、日历或文档。因此无需 DWS 授权，也不读写真实钉钉个人产品数据；用户明确要查真实钉钉个人数据时，走独立的 DWS / mcall 授权链路。

### 1.1 边界：注册层硬限制

Runtime 仅在 `human.config.channelKind === 'p2p'` 时把该工具推入工具列表（`human/tools.ts:477-479`），群聊实例的工具列表中**不存在**它。这不是提示词层面的软约束，而是工具注册层的硬限制，并由测试锁死。

| 场景 | 可否调用 | 说明 |
| --- | --- | --- |
| 恩熙 1v1 私聊（钉钉 / Web） | 是 | 汇总当前用户可见的多个项目群看板 |
| 恩熙所在的某个群聊 | 否 | 群内应查看/操作当前群看板，用 `query_group_board` |
| 查询真实钉钉待办 / 日历 / 文档 | 不走本工具 | 进入 DWS / mcall 授权链路 |
| 用户不可见的群 | 不进入结果 | 数据源按当前用户可见实例过滤 |

### 1.2 只读

工具运行分组为 `read`：不创建、不修改、不关闭任何看板数据。协作待跟进项由 tm-console 旁路扫描写入看板，本工具只读转发。

## 2. 数据来源与聚合规则

### 2.1 读取链路

```text
当前 1v1 用户 empId
  → server my-instances（只取该用户可见的群实例，排除个人会话）
  → scene-group.metadata.board（群聊项目看板）
  → 归集五类事项，生成 personal_work_summary payload（version 2）
  → 回复末行强制附 [查看协作摘要](panelUrl)
  → Web 右侧 Panel 或钉钉第四屏（前端重新聚合当前数据后渲染）
```

`empId` 优先取 p2p channel 的 `empId`，回落 `human.config.empId`；取不到时直接返回失败，不生成误导性空摘要。

### 2.2 五类事项

| 分类（payload 字段） | 判定规则 | 实现位置 |
| --- | --- | --- |
| **协作待跟进项** `collaborationItems` | 只读转发 `getOpenCollaborationItems(board)`：`status === 'open'` 且 `sourceUpdatedAt` 未超 14 天（`COLLABORATION_STALE_DAYS`）。本工具不自行判定 | `groupBoard.ts:635-660` |
| **已过期里程碑** `milestones` | `status !== 'done'` 且日期可解析且 `dueTime < 今日零点`，按到期时间升序 | `index.ts:204-241` |

| **@我的事项** `actionItems` | 扫 `board.events` 与 `board.content` 两段 markdown，匹配 `(?:@|＠)\s*<候选词>`；候选词 = 花名 + empId 的 5/6 位补零变体 | `index.ts:281-319` |

| **数字人产物** `artifacts` | `getVisibleArtifacts` 过滤废弃预发链接后按 `at` 倒序取前 N，**无时间窗口** | `index.ts:321-352` |
| --- | --- | --- |

协作待跟进项的四种类型（`CollaborationItemKind`）：待决策 `awaiting_decision`、待反馈 `awaiting_response`、待验收 `awaiting_acceptance`、外部依赖 `blocked_by_dependency`。

### 2.3 数量边界

| 参数 | 值 | 位置 |
| --- | --- | --- |
| 最多扫描群数 | 80 | `DEFAULT_MAX_GROUPS` |
| 实例列表每页 | 100 | `PAGE_SIZE` |
| 每类返回条数 | 默认 10，硬上限 10（工具参数 `limit` 可传 1–10） | `MAX_ITEMS_PER_SECTION` |

### 2.4 失败语义

读取实例列表失败时返回 `success: false`，**不降级为空态**（`index.ts:403-409`）。理由：空摘要与"你确实没有待办"在用户端无法区分，一次接口抖动会被读成"我没事可做"。

## 3. 输出与链接协议

### 3.1 工具输出形态

工具返回的不是裸 JSON，而是一段带下游约束的文本：`结果: <JSON>` + `下一步输出要求（必须遵守）` + `最后一行必须追加: [查看协作摘要](<panelUrl>)`。模型最终回复必须用简短 Markdown 说明结果、不粘贴工具 JSON、末行附摘要链接。

`panelUrl` 按 `viewerSource` 分流（`personalWorkSummaryTool.ts:22-36`）：`web-private` → https 裸链；其余 → 钉钉协议 URL。

### 3.2 出站改写

`normalizePersonalWorkSummaryPanelLinks(content, protocol, context)`（`linkBuilder.ts:319-337`）在消息出站时统一处理链接，调用点三处：`TmClient.streamReply`（:612）、\`streamReplyV2\`（:700）、`card/turnRunner`（:65）。

行为是**改写已有链接的协议**，而非补齐缺失链接：`protocol === 'web'` 时原样返回；否则把 `[查看协作摘要](.../collab/summary-panel...)` 以及裸 URL 一并替换为钉钉协议。链接本身由 prompt 硬约束 + 工具 output 约束两道保险保证模型会输出。

### 3.3 钉钉第四屏协议

```text
dingtalk://dingtalkclient/action/open_platform_link
  ?pcLink=<enc(dingtalk://.../open_side_popup_wnd?url=<enc(https://.../collab/summary-panel?ddtab=true&summaryPanelVersion=…)>)>
  &mobileLink=<enc(https://.../collab/summary-panel?summaryPanelVersion=…)>
```

*   **PC** 走 `open_side_popup_wnd` 右侧侧滑窗，内层 https 带 `ddtab=true`，随 `pcLink` 二次编码。
    
*   **移动端**是**裸 https**，不包 `open_mini_app`（与群看板 `buildGroupBoardUrl` 走 `wrapFourthScreen` 的 float 小程序面板不同）。
    
*   `summaryPanelVersion` 为 cache-bust 参数（默认 `summary-panel-v2`，可由 `SUMMARY_PANEL_VERSION` / `RUNTIME_VERSION` 覆盖），用于绕过钉钉 webview 缓存。
    
*   群上下文下先进 `/collab/cover?...&source=summary-panel&redirectUrl=...` 做成员校验（`guardGroupCollabEntry`），个人上下文直达。

## 4. 前端呈现

### 4.1 Web 1v1 主会话

仅当 `currentInstance?.type === 'personal'` 时拦截摘要链接（`useDingTalkBindings.ts:65`）；群聊会话里出现同类 URL 按普通 Markdown 链接处理。识别的路径有三条：`/collab/summary-panel`、`/collab/pilot-summary`、`/pilot-summary`。

普通左键点击在 Pilot 页面右侧打开 `SummaryPanel`，不离开 1v1 会话；带修饰键、非左键等原生打开行为按普通外链处理。

面板提供：分区统计、每分区限量展示（默认 4 条，群概要事件与产物各 10 条）、点击事项按 `sessionId + focusSection + focusTarget` 回到对应群看板位置。

### 4.2 钉钉第四屏独立应用

`apps/summary-panel` 是独立构建入口（路由 `/collab/summary-panel`，开发端口 5183），与 Web 右栏复用同一个 `PersonalWorkSummaryCard`。

两处宿主的差异：独立入口 `showMilestones={false}`（不显示里程碑分区），且点击事项优先调钉钉 JSAPI `dd.biz.chat.toConversationByOpenConversationId` 跳回原始项目群（`packages/shared/src/dingtalk.ts:438-443`），JSAPI 不可用时才降级打开带定位参数的 Web 页面。

### 4.3 完整卡片不反序列化工具输出

工具调用历史仍以通用工具卡呈现，方便排查；但完整视觉卡片**不从这段历史 JSON 反序列化**——Web 右栏与钉钉第四屏都重新聚合当前数据再渲染。

理由：用户点击摘要链接时应看到当前最新的可见群看板状态，而不是工具调用那一刻的旧快照。代价见 §6.1。

## 5. 关键设计决策

| # | 问题 | 决策 | 理由 |
| --- | --- | --- | --- |
| 1 | 如何保证"个人跨群视角"不污染群内上下文 | 按 `channelKind` 在**工具注册层**排除，而非写进 prompt | 提示词约束会被长上下文冲淡；注册层排除使群聊实例根本看不到这个工具，且可被测试锁死 |
| 2 | 面板该展示工具调用时的快照，还是当前状态 | 前端重新聚合，工具输出只用于聊天内的文字摘要 | 用户从收到消息到点开面板可能间隔很久，快照会展示已解决的事项 |
| 3 | 钉钉与 Web 的链接协议差异放在哪层 | 工具产出 web 裸链，**出站层**按 `viewerSource` 改写 | 工具不需要知道下游渠道；同一份工具输出可服务 Web/钉钉/卡片三条出站路径 |
| 4 | 四个界面（吊顶、个人摘要、群看板、query 工具）会不会显示不同的待跟进集合 | 过滤与排序收敛到单一入口 `getOpenCollaborationItems` | 各处自行过滤必然漂移；集中后 14 天陈旧阈值等口径只有一处 |
| 5 | 数据读取失败时展示什么 | 返回 `success: false`，不返回空摘要 | 空态与"真的没有待办"不可区分，会误导用户 |
| 6 | 钉钉 webview 缓存导致面板不更新 | URL 带 `summaryPanelVersion` cache-bust 参数 | 发版后用户无需清缓存 |

## 6. 当前限制

### 6.1 文字摘要与面板存在两套聚合口径

§4.3 的"前端重新聚合"换来了数据新鲜度，代价是 runtime 与 web 各有一份聚合实现，口径已经产生漂移：

| 维度 | runtime | web |
| --- | --- | --- |
| payload version | 2 | 1 |
| 待跟进段 | `collaborationItems`（14 天陈旧过滤） | `blockers`（legacy markdown），且被 flag 关闭 |
| 扫描实例 | 80 个，翻页，只 `ddGroup` | 50 个，只第 1 页，不过滤类型 |
| 产物时间窗口 | 无窗口 | `at >= 本周一 00:00` |
| @我 数据源 | events + content | events + blockers + content |
| `focusSection` 枚举 | 含 `collaboration` | 含 `blockers`，无 `collaboration` |

其中协作待跟进项在 web 侧由 `SHOW_BLOCKERS_IN_PERSONAL_SUMMARY = false`（`loadPersonalWorkSummary.ts:33`、`PersonalWorkSummaryCard.tsx:21`）编译期关闭，注释为"卡点数据继续保留在群看板，协作摘要暂不对用户展示，待方案完善后再开启"。

**收敛方向**：让 web 面板直接消费 runtime payload，或至少把 web 聚合对齐到 `collaborationItems` 并去掉周窗口——而不是长期维持两份实现。

### 6.2 其他

*   `prompts/task-routing.md` 中的摘要链接写死了 pre 环境域名。钉钉通道由 `normalizePersonalWorkSummaryPanelLinks` 的路径正则兜住（匹配任意 host），但 `protocol === 'web'` 直接返回不改写，Web 私聊下模型输出的 pre 域名会原样落地。
    
*   web 侧无测试覆盖（runtime 侧有 7 个聚合用例 + 链接协议与出站改写用例）。
    
*   `awaiting_acceptance`（待验收）目前无上游来源映射。

## 8. 设计演进与取舍

### 8.1 卡点：从"LLM 写入"到"旁路扫描 + 只读消费"

**原设计**：卡点是看板的 `blockerItems` 字段，由主 agent 和 reflection 通过 `update_group_board` 工具写入，摘要读 `blockerItems`、legacy `blockers` markdown 作兜底。

**为什么改**：让模型直接写结构化卡点，暴露了三个问题——模型措辞每轮抖动导致同一件事反复新增；`proposedSolution`（建议）与 `resolution`（已解决）被混用，卡点被过早关闭；以及"无响应满 N 小时"这类**时间条件在 turn 驱动的链路里根本判不了**（群完全静默时不产生 turn，而静默恰恰是最需要判定的时刻）。

**改成什么**：卡点真值移出看板，由 tm-console 旁路扫描群消息生成、server 侧维护状态机；看板上只保留 open 项的派生投影 `collaborationItems`；`BOARD_FIELDS` 不再接受该字段，runtime 与 Web 全部改为只读消费。语义判定归模型（"这是不是一件在等的事"），时间与合法性判定归代码。

**代价**：多了一条旁路链路和真值/投影一致性问题（靠每次看板写盘顺带重派生来自愈）；以及本文档 §6.1 的 web 侧尚未接入。

### 8.2 摘要分类：4 类 → 5 类，并去掉产物时间窗口

原设计是「过期里程碑 / 卡点 / @我 / 新文档」四类，其中"新文档"限定最近 7 天。

实际使用中发现两点：一是用户在 1v1 里问的"最近怎么样"往往想知道**项目发生了什么**，而四类里没有承载群概要的分区，于是新增 `updates`；二是 7 天窗口会让摘要在项目平稳期变成空的——用户想找的产物文档往往是一两个月前归档的，时间新鲜度不是它的相关性指标，于是去掉窗口改为按时间倒序取前 N。

### 8.3 链接补齐 → 链接改写

原实现有一个 `textStreamer` 在最终回复里**检测本轮是否调用了该工具，若模型遗漏链接则补齐**。后来该文件整体移除，改为出站层只做协议改写。

原因是"补齐"要求出站层理解本轮的工具调用语义（还要兼容 `tool_name` / `data.turnId` / `tool_result` 多种形态），耦合重且易漏；而把"必须输出链接"下沉为 prompt 硬约束 + 工具 output 约束两道保险后，出站层只需做无状态的字符串协议替换，职责更干净。
