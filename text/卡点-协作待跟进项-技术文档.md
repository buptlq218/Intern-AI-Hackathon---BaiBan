# 卡点-协作待跟进项-技术文档

# 协作待跟进项（卡点）识别与跟踪 · 技术文档

> 领域模型口径 v3.2。本文描述系统的**最终形态与设计依据**；所有被推翻过的方向、以及"为什么不是另一种做法"，集中记在 §17。 文中出现的量化结论均来自真实群语料回放或灰度实测，不是构造用例。

---

## 1. 背景与目标

### 1.1 问题

数字员工"恩熙"在钉钉群里旁听并参与协作。产品上希望她能回答一个问题：**这个群现在有什么事卡着、卡在谁身上、下一步要做什么。**

重写之前，系统里同时存在三套"卡点"表示：

| 表示 | 产生方式 | 实际状态 |
| --- | --- | --- |
| 看板 markdown 里的 `## 卡点` 段 | LLM 直接往看板文本里写 | 写入随机、格式漂移，前端靠正则解析 markdown 表格 |
| `BlockerEntry` 结构 + `SOLUTION_PLACEHOLDERS` | 前端解析后的中间态 | 解析失败即静默丢弃，占位符污染展示 |
| 个人工作汇报里的卡点段 | 由 `SHOW_BLOCKERS_IN_PERSONAL_SUMMARY` 开关控制 | 开关从未置 true，整块是死代码 |

三套表示没有一套是可信真值：没有状态、没有时间、没有责任人锚定、没有关闭条件，也没有任何一条能回查原文。结论是**这三份都是死数据**，不能在上面做增量。

### 1.2 产品前提：准确性优先

卡点会进两个高可见度出口——群吊顶看板、个人工作汇报。这两处出错的代价不对称：

*   **漏报**一条卡点：用户看不到某件事，损失有限；
    
*   **乱报**一条卡点：恩熙会去催一个不存在的事、或者催错人，直接损伤"数字员工可信"这个产品根基。
    

因此全链路口径统一为：**宁可不报，也不要乱报**。后文所有"看起来过于保守"的阈值与闸门，都源自这一条。

### 1.3 目标

1.  卡点成为**有状态、有时间、有责任人、可回查原文**的一等领域对象，真值落库；
    
2.  判定语义与判定实现分离，离线可回放、可拟合、可量化；
    
3.  判定分工明确：**凡是代码能判的绝不交给便宜模型**；
    
4.  灰度可控、可急停；前端只做只读投影展示，不承担任何判定。

## 2. 架构

### 2.1 职责划分

```plaintext
配置中心（灰度名单唯一真值源）
   │  tm-console 订阅 → server 单事务写配置表两闸
   ▼
┌─────────────────────────────────────────────────────────────┐
│ runtime（ncode-pilot-runtime） · 判定层                      │
│   reflection 框架 → followupAspect                          │
│     · 语义抽取 / 响应分级 / 关闭出口     ← LLM               │
│     · 工作小时计时 / 升格 / 过期 / 回收   ← 纯代码            │
│     · 三层过滤（结构 → 名册锚定 → 近似去重）                 │
└───────────────┬─────────────────────────────────────────────┘
                │ 唯一写口
┌───────────────▼─────────────────────────────────────────────┐
│ server · 真值层（最终防线）                                   │
│   ncode_pilot_project_followup_item   真值（六态）            │
│   ncode_pilot_project_event           事件（append-only）     │
│   迁移白名单 + CAS / closeNote 强制 / uk_item_id 收敛          │
│   ncode_pilot_group_config            群级两闸（行级单源）     │
│   open-projections                    展示（读时即时派生）     │
└───────────────┬─────────────────────────────────────────────┘
                │                       ┌──────────────────────┐
┌───────────────▼──────────────┐        │ nc-pilot-web         │
│ tm-console                   │        │  BoardCollaboration- │
│   日批兜静默群的时间规则      │        │  Items（只读展示）    │
│   定向催办：私聊通知卡        │        │  单一过滤入口         │
└──────────────────────────────┘        └──────────────────────┘
```

四层的边界是硬的：**判定只在 runtime，真值与展示派生只在 server，时间兜底与触达只在 tm-console，展示只在 web。** 后面每一节都可以看作对这条边界的具体化。

### 2.2 为什么挂在 runtime reflection 上

卡点判定需要**看到群里的人际对话**。可选挂载点有三个：独立定时任务扫消息表、群消息回调实时判定、挂 runtime 的 reflection 框架。选 reflection 有三条依据：

1.  **数据在这里最完整。** reflection 的对话窗口就是恩熙实际看到的上下文，包含 @ 她的消息与旁听接进来的人际对话。绕开 runtime 从消息表反查，拿到的是残缺视图（§8.1 两套语料的对比即此）。
    
2.  **成本已被摊薄。** reflection 是既有机制：`everyTurns=3` 触发，多个 aspect（boardAspect / memoryAspect / followupAspect）**共享同一次便宜模型调用与同一个游标**。新增 aspect 的边际成本只是 prompt 里多一段 schemaHint，不是多一次调用。
    
3.  **失败语义已经定义好。** 游标推进、单飞、重试都由框架统一负责，aspect 只需在真写失败时返回 `false`。
    

代价是判定节奏与 reflection 绑定：**静默群不产生 turn，时间规则就不会跑**。这一条由 tm-console 日批补齐（§10）。

### 2.3 分层与文件

| 层 | 文件 | 性质 |
| --- | --- | --- |
| 判定纯函数 | `src/human/reflection/followup/model.ts` | 无 IO。计时 / 状态机 / 去重 / 截断 |
| 计划纯函数 | `src/human/reflection/followup/planner.ts` | 无 IO。现状快照 + 模型输出 → 动作列表 |
| 编排 | `src/human/reflection/aspects/followupAspect.ts` | 闸门 → 读现状 → 计划 → 执行 |
| 写口 | `src/human/reflection/followup/store.ts` | 打 server，失败分级 |
| 窗口清洗 | `src/human/injectedText.ts` | 剥 runtime 注入文本 |
| 离线回放 | 独立仓外工具（原 `src/human/followup/replay.ts` 已移出仓） | 与线上共用 model / planner |

**关键约束：**`**planner.ts**` **与** `**model.ts**` **是纯函数，线上 aspect 与离线回放 harness 共用同一份。** 执行侧不同（线上打 server，harness 改内存表），计划侧只有一份。这是"回放结论 = 线上结论"的实现基础，也是整个拟合工作能成立的前提。

## 3. 领域模型

### 3.1 六态状态机

```plaintext
                        ┌─→ false_positive (S5)
  candidate (S0) ───────┼─→ expired        (S6)
       │                └─→ open (S1)
       │                        │
       └─ discard（软删）        ├─→ resolved_explicit (S2)
                                ├─→ resolved_implicit (S3)
                                ├─→ obsolete          (S4)
                                ├─→ false_positive    (S5)
                                └─→ expired           (S6)
```
```ts
const TRANSITIONS = {
  candidate: new Set(['open', 'false_positive', 'expired']),
  open: new Set([...TERMINAL]),   // 五个终态
};
// 终态无出边
```

设计要点：

*   `**candidate**` **是"被提出但还不是卡点"。** 不投影到界面、不进任何仪表盘分母。绝大多数请求在候选期内就被正常协作接住，这样界面零噪音。
    
*   `**candidate**` **不能直接 →** `**obsolete**` **/** `**resolved_***`**。** 语义上"从未成立的东西不能算解决"。候选期内被办完的走 `discard`（软删）+ 事件留痕，见 §6.6。
    
*   `**expired**` **不是"解决"。** 它不进解决率分子，也不投影到界面。
    
*   迁移白名单在 runtime `model.ts` 与 server 侧**各有一份且互为镜像**——runtime 提前判定避免无效请求，server 是最终防线。
    

`blockedOn` 三值，判据是"当前这一跳有没有可指名的人能动手"：

| blockedOn | 含义 | 投影 kind |
| --- | --- | --- |
| `confirm` | 等一个明确说法 / 决策 | `awaiting_decision` |
| `action` | 等一个动作 | `awaiting_response` |
| `external` | 纯外部条件 | `blocked_by_dependency` |

### 3.2 真值 / 事件 / 投影 三层

| 层 | 位置 | 语义 |
| --- | --- | --- |
| 真值 | `ncode_pilot_project_followup_item` | 唯一真值。六态、时间戳、责任人、证据句 |
| 事件 | `ncode_pilot_project_event`（aspect=followup） | append-only。响应 / 敷衍 / 候选期内办完 / 升格 / 关闭 / 已通知 |
| 投影 | `open-projections` 接口（读时从真值表即时派生） | **纯派生**，只为展示，不落库、可随时重算 |

这一层拆分解决的是重写前最本质的问题：**看板 markdown 既是展示又是真值**，于是任何一次展示改动都在动真值。现在投影连存储都没有——每次读取都从真值表现算，不存在"投影和真值不一致"这种状态。

判定侧的一条硬规则：**briefing（给模型看的现状段）只读真值表，绝不读展示派生。** 展示是派生物，用它做判定输入等于让模型基于二手视图判断。

### 3.3 投影映射

投影在读取时由 server 从真值表即时派生（`open-projections`，§9.4），**只含** `**open**`：

*   `candidate` 不投影 → 候选期界面零变化；
    
*   `obsolete` / `false_positive` / `expired` 不投影 → 它们都不是"解决"，投成 resolved 会污染界面语义；
    
*   `resolved_*` 也不投影 → 卡点被解决时的表现是\*\*"从投影里消失"，而不是"变成已解决"\*\*。这是刻意的产品表达：用户不需要手动关闭，也不需要看到一条已完成的残留项。
    

排序在派生函数里定死：按 `sourceUpdatedAt`（提出 / 升格 / 最近活动 / 关闭四个时间取最大）倒序，再按 id 兜平——**派生结果是全序的，不依赖数据库返回顺序**，任何一次读取都收敛到同一份。

一处技术债：`CollaborationItemKind` 里的 `awaiting_acceptance` 没有任何 `blockedOn` 能映射到它，是**死枚举值**。当前无功能影响，但应当清理或补映射。

## 4. 判定分工

**全链路唯一一条设计红线：凡是代码能判的绝不交给便宜模型。**

| 判定 | 归属 | 理由 |
| --- | --- | --- |
| 这段对话里有没有新卡点 | LLM（runtime） | 纯语义，代码不可能判 |
| 响应三分级（实质响应 / 明确敷衍 / 不算响应） | LLM（runtime） | 语义 |
| 四个关闭出口（resolved ×2 / obsolete / false\_positive） | LLM（runtime） | 语义 |
| 候选挂了多少工作小时 | 代码（runtime） | 算术。**算好了写进 prompt**，模型不做算术 |
| 到点升格 / 到期过期 / 候选回收 | 代码（runtime + tm-console） | 时间 |
| 状态迁移是否合法、是否并发撞车 | 代码（runtime 预判）+ server（CAS 终裁） | 结构 |
| `closeNote` 是否必填 | server | 结构 |
| 责任人是谁 | 代码锚定（名册唯一命中） | **模型只有建议权**，`empId` / `name` 一律用 server 值 |
| 证据句是否真出自窗口 | 代码（`isEvidenceInWindow`） | 可判定 |
| 字段长度 | 代码（写出去之前截断） | 不指望 server 帮忙 slice |

这条红线必须**在类型边界上强制，不能写在 prompt 里**。反例是曾经存在的一条破口：模型输出的 `action` 裸 `as FollowupStatus`，只靠迁移白名单兜底，而 `expired` 与 `open` 恰好都是合法迁移目标，于是两条越权路径都能穿透：

*   `{"action":"expired"}` → 一句随口证据就把一条 open 真卡点判死。它是终态、不投影（界面无痕消失）、又不进解决率分子，**连"虚高解决率"这个可观测副作用都没有**，比错判 resolved 更难发现；
    
*   `{"action":"open"}` → 候选直接升格，**完全绕过 12 工作小时条件**。
    

prompt 末尾"升格 / 过期 / 回收由代码按时间判，不要输出这三类动作"那句是纯提示、零执行力。现行做法是结构闸 `MODEL_CLOSURES` 白名单：不在集合里一律 `skip`（留痕不落库），让越权意图**可见**而不是静默生效。

## 5. 计时语义

### 5.1 工作小时

```ts
workday: { fromHour: 10, toHour: 20, tzOffsetMinutes: 480 }
openHours: 12          // 条件②：累计无响应工作小时
expireDays: 7          // 自然日，不折算
candidateTtlHours: 48  // 候选回收（自然小时）
```

三处设计：

1.  **用固定偏移算，不依赖进程 TZ。** 沙箱 TZ 不保证，`shift(ms) = ms + 480min` 后当 UTC 读，就得到 +08:00 的日历值。
    
2.  **夜间与周末零推进。** 下班过夜、周末沉默不是"无响应"信号，把它算进去会让周一早上凭空冒出一批假卡点。
    
3.  `**expireDays**` **走自然日而非工作日**，因为它的语义是"这件事已经彻底没信号了"，不是"对方欠我多少工时"。
    

### 5.2 起算锚点与清零

```ts
promotionStartAt = max(mentionedAt, lastActivityAt ?? 0)
```

*   `mentionedAt` 只在新建时写，**复提不会推后**（server upsert 的 update 分支不碰 `mentioned_at`）。隔天追问是"它变痛了"的信号，不该让计时重新开始。
    
*   任何一次**实质响应**把 `lastActivityAt` 搬到当前时刻，计时清零。
    
*   **明确敷衍不清零**——纯拖延语（"我得看看"）只落事件，不动时间。这一档从严认定：分不清时默认对方在处理，按 `response` 走。
    
*   **模型给的** `**at**` **不允许移动计时起点。** 提出时刻会被夹进 `[窗口最早消息, now]`（上下界都夹），夹过在 `payload.atClampedFrom` 留痕。这道闸是必需的：实测出现过模型把 `at` 写早三天，起点一旦被移到窗口之外，"挂够时长"这个语义条件被整个跳过，日期盐也让跨天复提识别失效。选择**夹而不拒**：判据句必出自窗口（§6.2 已保证），"这件事发生在窗口内"是已证事实，夹到窗口起点是最紧的可辩护下界；拒掉会因一个日期笔误漏催真卡点，方向更糟。上界同样要夹，否则 `at` 写成未来会让它永远升不了格。
    

### 5.3 算例

设某条候选周五 18:00 被提出（工作时段 10:00–20:00，阈值 12h）：

| 时刻 | 累计工作小时 | 判定 |
| --- | --- | --- |
| 周五 20:00 | 2.0 | 候选 |
| 周六 / 周日全天 | 2.0（零推进） | 候选 |
| 周一 20:00 | 12.0 | **到点升格 open** |

注意周一 20:00 时距提出已过 74 自然小时 > `candidateTtlHours` 48h。这就是下一条为什么重要。

### 5.4 优先级：升格优先于回收

```ts
if (shouldPromote(...))            { /* → open */ }
else if (shouldExpire(...))        { /* → expired */ }
else if (shouldDiscardCandidate()) { /* → discard */ }
```

`if / else if` 的顺序即优先级，**这是刻意的**：反过来会把"跨了周末但已挂满工作小时"的真卡点当垃圾删掉——而 §5.3 那个形状恰好是领域模型里最痛的一类卡点。

因此"48h 回收可能吞掉真卡点"这个担忧在**纯工作日内不可达**（48 自然小时内必然已积累满 12 工作小时并先行升格），只在**跨周末**时理论可达，而正是那种情况被这个优先级顺序挡住。

### 5.5 已知偏差：法定节假日

`workingHoursBetween` 只通过 `isWeekend` 排除周六周日，**不识别法定节假日**。国庆、春节这类连续假期期间，累计工作小时会照常推进，导致节后出现一批不该成立的升格。

这是当前最明确的一条待修偏差。修法有两条：接节假日日历服务，或在 `workday` 里加一份可配置的例外日期集合（后者与 §9.5 的"计时口径不可配置"原则冲突，需单独讨论）。

## 6. 准确性防线

从模型输出到落库，一共六道相互独立的闸。它们全部服务于 §1.2 那条口径：宁可不报，不要乱报。

### 6.1 三层过滤

模型给的每一条 `new`，依次过：

**① 结构层** — 迁移白名单 / 关闭出口白名单 / 证据必填 / 字段截断。 **② 名册锚定** — `waitingOn` / `requestedBy` 必须在群成员名册里**唯一命中**才认；命中后 `empId` 与 `name` 一律用 server 值。命中 0 或 ≥2 个，该字段直接省略。 **③ 近似去重** — 见 §6.5。

新建还有一组独立的必备项（`buildNewItem`）：

```ts
if (!mentionedAt || !unblockAction || !isEvidenceInWindow(evidence, input.conversation)) return null;
if ((blockedOn === 'action' || blockedOn === 'confirm') && !waitingOn) return null;
```

即：必须有可解析的提出时刻、必须有可验收的解除动作、证据必须能回指清洗后的真人原话；`action` / `confirm` 还必须有可催办的群成员（`external` 可以没有人，但一样要写清外部解除条件）。**少任何一项宁可不建。**

### 6.2 证据窗口溯源

`isEvidenceInWindow(evidence, windowText?, minQuoteLength = 6)` 判断"这句证据是不是真的出自本次新增对话"。

三个参数选择都有实测依据：

*   `**QUOTE_ANCHOR_LEN = 10**`**（锚点长度）**：模型抄原文时常带说话人前缀、补上下文尾巴、或被 `FIELD_LIMITS` 截断，要求整句连续命中会误拦真引用；反过来，连续 10 个归一化字符（中文即 10 个汉字）在几十条消息里凑巧撞上的概率可忽略，编造句过不了。
    
*   `**MIN_QUOTE_LEN = 6**`**（证据句长度下限）**：这一条修的是一个方向反了的判据。原实现对 `quote.length <= QUOTE_ANCHOR_LEN` 的短句要求整句命中，注释以为"更严"，但对高频套话恰恰**更松**——窗口里出现"已完成"几乎是每天的必然事件，于是三个字就能走通 `false_positive` 把一条真卡点无痕删掉（实测 `已完成` / `好的收到` / `收到` / `好的` 全部放行，`closeNote` 就落成那三个字）；而真正的反证句"这条当初就抽错了"（8 字）反倒因为要整句命中被拦。**这道闸的强度原先与证据句的反证力成反比。** 取 6 是因为上面那批套话最长 4 字，而能独立说明"这件事当初就不该建"的句子在中文里到不了 6 字以下。
    
*   **逐字符滑窗而非按 10 字跳步**：模型常在原文前加"某人："前缀，跳步会恰好跨过唯一能命中的锚点，把真实证据拒掉。
    

两处补充：说话人前缀（`/^(?:\[[^\]]+\]\s*)?[^:\n]{1,32}[:：]\s*/`）会被剥掉后作为**候选之一**再比一次（同时保留原串，避免把业务正文里的冒号误当前缀）；`response` / `acknowledged` 显式传 `minQuoteLength = 1`，因为"收到"也是真实响应，但仍必须逐字出现在清洗后的窗口里。

**缺窗口时一律拒绝（fail-closed）。** 缺输入不是放行理由。

### 6.3 false\_positive 双通道

`false_positive` 是**删真值**：项目从表里消失，不进解决率也不进任何分母，界面上无痕。所以它是唯一需要双通道把关的出口：

*   **prompt 侧**：只在【本次新增对话里出现直接反证】时才允许，没有新材料就不要翻旧案；
    
*   **代码侧**：反证句必须逐字出自清洗后的窗口。
    

只靠 prompt 那一句挡不住——卡点的出生原文早已滑出窗口（`MAX_WINDOW=60`），现状段也不给 `evidence`，所以模型"重审旧案"时手上没有任何材料，它唯一能做的就是编一句话。

口径一律往严的靠，因为两个方向代价严重不对称：误拦一条真误报，它最多挂到 7 天 `expired`（不算解决）；误放一条编造反证，就是**无兜底地删掉一条真卡点**——产品口径是卡点不做人工关闭、只由恩熙判断，人工改判口已取消，这道代码闸是唯一兜底。

### 6.4 关闭必须自证对齐（`satisfies`）

`resolved_explicit` / `resolved_implicit` 除了证据句，还必须带 `satisfies`：显式说明"这条 item 等的是 X，而上面那句原文说明 X 已经发生"。说不出就不关。

这一条的必要性由真语料复盘给出：关错的主要形态是**证据错配**——模型从本段挑一句最像"交付完成"的话贴到另一件事上（item 等的是 AWS 账户验证，证据却是"视觉复核完成"；item 等的是 anpm 凭证，证据自己写着"但 publish 接口不接受"）。

同一条口径下 prompt 里还固化了几个实测出来的边界：

*   evidence 自带转折否定不算解决（"凭证拿到了，但接口不接受"）→ 判 `response`；
    
*   引"事情已经做完"那句，不要引"有人回话了"那句；
    
*   只是表态或做了选择、没有交付结果 → `response`；
    
*   仍在商讨 / 澄清范围 / 收集信息 / 排期 → 不是已解决；
    
*   **请求方撤回或转手 → 判** `**obsolete**`：转手若被判成 `resolved_explicit`，会同时抬高解决率并吞掉"绕行"这个信号（`obsolete` 不计入解决率，且它的占比本身就是绕行率的观测口）。
    

这里附一个重要的**负结果**：曾试过顺手加一句"resolved\_\* 只留给东西真的交付了"，结果连带抬高了交付路径的门槛（真语料 A/B：交付样本关闭率 14/15 → 10/15，5 次什么都不输出）。所以那两行注释里明确标注**只描述 obsolete**。这说明便宜模型上的 prompt 约束存在强耦合，任何"顺手加一句"都必须过 A/B。

### 6.5 近似去重

同根因复提要命中现存未终态项（更新而非新建，`mentionedAt` 保持最早），**跨日也要命中**。

标题比较走 **2-gram Jaccard 相似度**（阈值 `SAME_ROOT_CAUSE_SIMILARITY = 0.6`）而非精确匹配，原因是便宜模型每个 pass 独立描述同一件事，措辞必然抖动——实测同一条卡点两次分别被写成「板栗仁询问恩熙的 opencovid」和「板栗仁询问恩熙的 opencovid 信息, 等待回复」。只做精确匹配就会重开一条，同一个点在看板上出现两次。

两处细节：

*   **子串包含要过长度下限** `**MIN_CONTAINMENT_LEN = 8**`**。** 一句是另一句的子串通常意味着同一件事被细化，但短串包含多半是巧合（"发布"落在"发布文档"里）。8 是权衡下限：「提供开关类型（Diamond/Switch/管控台）」这类真实追问远超它，而"发布""建表"这种两三字短词包含纯属巧合，合并会丢掉一条真卡点。
    
*   `**unblockAction**` **也走相似度。** 精确比对会漏掉**子集**这种形状：旧条等"开关类型、key 名称、环境"，模型又新开一条只等"开关类型"——标题相似度 0.459 拦不住，而两句其实是包含关系，结果两条候选覆盖同一件事各自计时。
    

阈值方向偏保守：**宁可漏合并（多一条）也别把两件事合成一条（丢一条）。**

### 6.6 丢弃必须留痕

计划层不采纳模型的某个动作时，产出 `{ kind: 'skip', ref, wanted, why }`——**不落库，只为了让丢弃可见**。

这条机制的来历是一次量化：计划层原先是裸 `continue`，语料回放实测 **21 条关闭动作被静默丢掉，直接造出 5/5 条假升格**（她已办完却被判无响应），而日志里一个字都没有。

同一类问题的另一半是 `candidate → resolved_*` 这条路径。语义上"未成立不能算解决"是对的，但**这是主路径不是边缘情况**：真语料回放里 24 次关闭意图有 **17 次**落在 candidate 上。直接丢的后果同样被实测到——候选一路挂到到点升格，**5 条升格全是早已办完的假卡点**。

正确出口是**回收候选**：server 的 `discard` 是软删，证据行留在表里；真值表因此只含真正成立过的卡点，而"她办完了几件"从事件流数（`followup.resolved_as_candidate`）。回收路径的门槛不比合法关闭低——同样要求 `evidence` + `satisfies`，因为回收是无门禁的物理软删，不像 `transition` 有 `closeNote` 强制。

**一处仍存在的不对称**：`candidate → obsolete` 走的是裸 `discard`，不要求证据、也不落事件。理由是"没有她交付了这个信号"，但结果是这条路径删真值时零留痕，与本节其他路径的口径不一致，属于待收口项。

### 6.7 窗口清洗：准确性问题而非省 token

`apply` 用的是 `ctx.conversationClean` 而不是 `ctx.conversation`。`injectedText.ts` 剥掉 runtime 自己注入的文本，**按标记剥而不是按** `**hide**` **标志**，因为两种按 `hide` 的做法都不成立。27 个真实群语料（3974 个 text part）上实测：

| 现象 | 计数 |
| --- | --- |
| 「请基于上面的群聊上下文」 | 435 处，全部 `hide=true` |
| 带「等你响应」的 `[旁听职责转移]` | 350 处 `hide=true`，**85 处根本没标（19.5% 漏网）** |
| "凡 hide 就整段丢"会误删的、**真装着别人发言**的群聊上下文信封 | **94 个** |

在没开旁听的群里，那 94 个信封是他人对话的唯一载体。所以漏一批、又误删一批，只能按标记走。

**为什么这对卡点是准确性问题**：注入文本里写着「群聊里需要提醒某个成员**补信息 / 确认 / 接手 / 知会**时，调用 notify\_user」和「若其中有**明确等你响应、且你本轮回复尚未覆盖的他人诉求**」——这恰好是卡点判定的原生词汇表。它进抽取窗口，便宜模型就能从**指令本身**抽出一条"有他人诉求等恩熙响应"的卡点：`waitingOn` 锚不到人（「某个成员」不在名册）→ 无人可催 → 必然走满 12 工作小时升格 → 进吊顶与个人工作汇报 → 挂到 7 天 expired。而且**这句话在窗口里是真实存在的**，给抽取补证据溯源闸也拦不住，只能在窗口这一层挡。同理，`false_positive` 的反证锚点必须来自清洗后的窗口——否则等于让 runtime 自己写的行为指令去删真卡点。

效果与代价都能量化：注入片段对抽取窗口的污染率 **21.4% → 0.1%**，窗口 token 顺带省 **39.2%**，并有哨兵测试反向锁定（改回读脏窗口则测试变红）。代价是 `发起人: 花名 (工号 N)` 也被摘掉，而它是线上窗口里**唯一**的说话人标识（`historyToText` 一律渲染成"用户："），摘掉后模型更难判 `requestedBy`、可能少抽几条。这个方向是**漏报**，而留着模板换来的是**乱报**，按 §1.2 就该往漏的那边倒。

### 6.8 单 pass 限流

`MAX_NEW = 3`、`MAX_UPDATES = 5`。便宜模型一次灌太多既挤爆输出预算，也放大误报。

## 7. 灰度与急停

### 7.1 四道闸

| 闸 | 位置 | 判定时机 |
| --- | --- | --- |
| 必须是群 | `ctx.isGroup` | `enabled`，私聊零成本（不拉群） |
| 急停开关 | `isFollowupKilled()` 读环境变量 | `enabled` |
| 灰度点名 | server 群配置行级输出 `followupConfig.enabled` | `collect`（那里本来就要拉群） |
| 已开旁听 | server 群配置行级输出 `listenConfig.listenEnabled` | `collect` |

后两闸是**合取**关系。第四闸的理由：没开旁听的群，人际对话根本不进 thread，抽取只剩 @ 恩熙那部分，在这种群里出的卡点必然是残缺视图上的判断，不如不出。

急停开关只认显式的 `'0'` / `'false'` / `'no'`，**只能用来关不能用来开**——避免"环境变量拼错就等于全量放开"。

### 7.2 灰度名单的唯一真值源

两闸的唯一载体是 server 的群配置表，名单的唯一真值源是配置中心（Diamond `ncode_followup_gray_groups` / group `tm-console`）：

```plaintext
配置中心（唯一真值）
   │  tm-console：启动加载 + 变更回调 + 5 分钟兜底 reconcile
   │  解析不合法 = 整份拒绝（fail-closed）
   ▼
server  POST /scene-group/followup-gray-config    ← 灰度专用原子接口
   │  单事务内：锁群行 → 只写配置表两行
   ▼
ncode_pilot_group_config（唯一存储）
   │  群列表接口按行输出 followupConfig / listenConfig
   ▼
runtime（followupAspect 两闸）与 tm-console（日批两闸）读同一份行级输出
```

因此三条旁路入口全部关闭：不存在开关脚本；两闸**根本不在 metadata 里**，通用 `upsert-metadata` 从物理上够不到它们（metadata 侧的受保护键只余 `taskLedger` / `aone` / `metricsExclude` 这些与卡点无关的既有键）；单独改旁听的老路由仍在，但同样只写配置表，5 分钟内会被 reconcile 按名单压回——**在 admin 里手动开关旁听会被静默还原，这是预期行为**。运行状态查只读的 `GET /api/v1/followup/gray-status`。

这套链路上有三条不可省的机制：

*   **fail-closed。** 解析不合法即整份拒绝，绝不拿残缺名单去关群；同步失败时日批与发卡自动关闭（`gray-status.lastError` 非 null 即此状态）。
    
*   **写库权归属声明。** 配置里 `syncEnv` 必填，声明"唯一有权写库的环境"。多套环境共用同一个数据库、却各读自己的配置实例，而同步器是无锁 `setInterval`：两边名单只要有一个字不同，就会周期性互相翻转同一批群，而两边日志都打"applied 成功"。这类问题不能靠"保持两边内容一致"这种纪律兜——错一次就没人看得出来。归属声明把它变成机制：**非 owner 环境一行都不写、也不驱动日批与发卡**，`gray-status.syncOwner` 直接自证；判据是所有环境里**恰好一个** `syncOwner: true`。
    
*   **归属判据只看** `**followupConfig.enabled === true**`**。** 这一条决定 reconcile 的爆炸半径：若把 `listenEnabled` 也算进归属，库里所有自己开着旁听、与卡点无关的群都会被拖进 affected 集合，不在名单就被写 `listenEnabled: false`——共用数据库下等于一部署就批量关旁听。收窄后的实测接管面：全库 561 个群里只接管名单内的 1 个，旁听零误关。副作用要写清楚：**手动开了旁听、又想让卡点接管的群，必须显式进名单**，不会被自动扫进来。
    

### 7.3 急停的准确口径

`automation.notifyEnabled` **只刹 cron 那条自动车道**。手动口 `POST /followup/notify` 与 `/tick` 刻意不看它，也不看周末与环境检查——它们是人工验证与排障入口，带鉴权头就能执行。

**真正的急停是把群从名单里移掉**：两闸一关，日批扫到的就是 0 个群，手动口也找不到任何东西可推。另有两个更大范围的开关：runtime 侧 `NC_FOLLOWUP_ENABLED=0`（整个沙箱）、名单里的 `enabled: false`（全局）。

## 8. 离线回放与拟合

### 8.1 两套语料，互补且都不完整

| 语料 | 优点 | 缺陷 |
| --- | --- | --- |
| OSS `/scene-group/messages` | 有 `atUsers`；是完整群消息流 | **62% 的数字员工回复** `**text**` **为空** |
| `ncode_session_message.message_history` | 有恩熙的回复（99%） | 只有 thread 视图，看不到未进 thread 的人际对话 |

两套都用，原因是任何单一语料上的拟合结论都不可信：第一套缺恩熙的回复，而"恩熙自己把事办完了"是最高频的关闭形态（等她的事占一半以上）；第二套缺群里的人际对话，而那是卡点的主要产地。

第二套语料的三个实测坑都写进了 `corpus.ts` 的注释：内容在 `part.content` 而不是 `part.text`；`part.hide` 的段落是**装着别人发言的信封**不能整段丢；群名 / `openConvId` / `empId` 只出现在信封内部。

### 8.2 thread / full 双模回放量化覆盖差

`ReplayMode = 'thread' | 'full'`。同一份语料跑两遍，差值就是"旁听没接进来的那部分人际对话会让我们漏多少卡点"。这个数是"卡点必须依赖旁听"这个结论的定量依据，也是 §7.1 第四闸的来源。

### 8.3 线上离线同源

`slicePasses` 严格复现线上切窗语义：`everyTurns=3`、`maxWindow=60`、在下一个 turn 起点切断（因为线上是 `onTurnFinished` 触发）。`MemoryFollowupTable` 刻意复刻 server 的写入语义（迁移白名单、`closeNote` 强制、`mentioned_at` 不被 update 覆盖），而不是简单地"存下来就行"——否则回放里能落库的动作线上会被拒，拟合结论失真。

### 8.4 评测集导出工具链

评测 CSV 导出与回放 harness 同属离线工具链，现已**整体移出仓库**（原 tm-console 的 `evaluationCsv.ts` + `exportFollowupEvaluation.ts`，runtime 的 `scripts/replay-followup.ts` 一并删除）。移出的原因很具体：tm-console 的 Midway FaaS 构建没有 tsconfig include 白名单，仓内任何脚本都会被编译进产物，离线工具留在仓里等于持续为它付构建与依赖面代价。工具出仓后与线上仍共用同一份 `model.ts` / `planner.ts` 纯函数（§2.3），同源约束不变。

两处工程细节（随工具带出仓）：`safeCell` 对 `=` / `+` / `-` / `@` 开头的单元格做 Excel 公式注入防护；CSV 头部硬编码一句口径声明——**"仅包含 tm-console 实际接收并归档的群消息；不补拉数字人入群前的钉钉历史"**，防止标注同学把"语料里没有"误读成"系统漏抽"。

## 9. 工程化

### 9.1 稳定 id 与幂等

```plaintext
itemId = sha1(openConvId | normalize(title) | 提出当日)[0:32]
```

*   **与进程无关**：跨 sandbox 对同一件事算出同一个 id，表上 `uk_item_id` 收敛成一行；
    
*   **日期盐**：终态之后同事由再现是**新** item，不复活旧的——这同时是"错关"的自愈路径。
    

### 9.2 失败分级与共享游标

reflection 的游标是多个 aspect 共享的，所以 followupAspect 返回 `false`（不推进游标）必须极度克制：

| 失败 | 语义 | 处理 |
| --- | --- | --- |
| server 4xx | 判定被拒，属正常路径 | 不阻塞游标 |
| server 5xx / 网络 | 真写失败 | 返回 `false`，不推进游标 |
| 读卡点表失败 | 视图不完整 | 本轮整体跳过（**不基于半份视图判定**） |

若让 4xx 挡住游标，会连带 board / memory 两个 aspect 一起停摆。

### 9.3 并发与快照

`collect` 拉表和名册用 `Promise.all` 并行，结果存进 `SNAPSHOTS`（TTL 5 分钟）供 `apply` 复用，同一 pass 内不重复拉。**快照的** `**at**` **就是后面判定用的"现在"**，让 `apply` 的时间口径与模型看到的现状严格同一时刻——否则 collect 到 apply 之间的几秒钟会让"已挂工作小时"与判定基准错位。

同一群的 pass 由 reflection 框架保证单飞，不会交叠；跨进程的并发（reflection 与日批同时改同一条）由 server 的 CAS 兜（§11）。

### 9.4 展示派生：读时计算，不落库

投影经历过第二次收敛（第一次见 §17.9）：**从"写时落库重算"改为"读时即时派生"**。server 提供 `listOpenProjections()` 与 `POST /api/v1/project-followup/open-projections`，每次读取都从真值表现算 open 集合，投影本身不再有任何持久化形态。写路径上的投影维护逻辑（事务内重算、群行写锁、逐字比对跳过写入）随之整体删除，CAS 成为写侧唯一的并发锚。

三条由此得到的性质：

*   **不存在"投影与真值不一致"这种状态。** 派生物不落库，就没有漂移、没有脏投影、没有增量补偿逻辑，自愈问题被直接消解而不是被解决。
    
*   **两条升格路径的展示天然一致。** reflection 驱动与日批驱动只改真值，展示永远来自同一个读口。
    
*   **旧链路的残留被主动清退。** 历史上落过库的看板卡点键（`blockers` / `blockerItems` / `collaborationItems`）全部退役：通用写入入口经 `stripRetiredBoardCardpoints` 剥离这三个键（防止旧版本 runtime 整包写把旧投影再写回去），另有 `cleanup-legacy-cardpoints` 工具对存量数据做一次性物理清理。
    

### 9.5 计时口径不可配置

tm-console 的 `followupTime.ts` 是 runtime `model.ts` 计时常量的**逐字节镜像**，且刻意不做成可配置项。理由：两侧计时口径一旦能各自配置，就会出现"runtime 认为还没到点、日批认为已经到点"的双写打架，而这类不一致在生产上极难定位。代价是改阈值要动两个仓、两仓一起发版，接受。

配套的绊线用例断言的是**产品口径**而非当前值：`openHours === 12` ∧ 工作时段 `10:00~20:00`；所有跨天算例显式传 `{...DEFAULT, openHours: 12}`，不跟默认值走。这样任何一次为了调试放宽阈值或窗口，都会当场变红（原因见 §17.10）。

## 10. tm-console 日批

`POST /api/v1/followup/tick`，cron `0 5 10,15 * * *`（Asia/Shanghai），即每天 10:05 与 15:05。

**存在的唯一理由**：静默群不产生 turn，runtime 的时间规则就跑不到。日批只跑三条纯时间规则 + 候选回收，不做任何语义判定，也不调模型。

设计要点：

*   `isEnabled` 经 `followupGroupGate` 读 server 群列表的**行级配置输出**，与 runtime 两闸同一份单源（§7.2），天然无双源漂移；
    
*   controller 层**刻意忽略** `cronEnabled` / 周末 / 环境检查，让手工触发能绕过定时器的所有门禁（排障需要）；processor 层保留四道闸，`failed > 0` 抛错让调度可见；
    
*   server 返回的 409 归入 `stale` 并**单独记为** `**conflict**`：它是并发撞车的正常结果，判成 `failed` 会让整轮 tick 抛错。`conflict` 持续偏高说明两条升格路径在抢同一批群，是需要看的信号。
    

**一处待补**：`statusHistory` 没有时间下界，历史数据量增长后这条查询会线性变慢。

## 11. server 真值层

`src/function/projectFollowup.ts` 是唯一写口，写入语义收在 `src/service/projectFollowup.service.ts`。

基础约束：迁移白名单（与 runtime 互为镜像）、`resolved_*` / `false_positive` 强制 `closeNote`、upsert 的 update 分支**永不触碰** `**mentioned_at**`、读到 `gmtDeleted` 非空的行一律按 404 处理（软删行不可被同 id 写入唤醒）、事件 append-only、四个索引（`uk_item_id` / `idx_conv_status` / `idx_waiting_status` / `idx_aone`）。

四条并发与一致性机制：

*   **状态迁移走 CAS。** 条件是 `WHERE itemId + 旧 status + 未软删`，`affected !== 1` 直接返回 **409**。并发撞车只会被记为 `conflict`，不会后写覆盖先写、也不会落第二条事件。锁序固定为"先更新卡点行、最后才锁群行"，禁止新增反向锁序的路径（灰度配置接口同样是先群行、再配置表）。
    
*   `**upsert**` **只允许列白名单的条件** `**update()**`**。** 不能用 ORM 的 `save()`：它会在事务内重新 SELECT 再与内存实体 diff，于是内存里那个**从未被碰过的 stale** `**status**` 也算成"改动"写回去——能把别人刚提交的迁移降回 `candidate`，或让已回收项复活，等于在 CAS 背后开一个无 CAS 的后门。写完**重读拿真值**，避免后续判定用过期状态。
    
*   **并发首建有兜底。** 两个进程同时判定"这条不存在"并各自首建同一个 itemId 时，`uk_item_id` 让输家撞 `ER_DUP_ENTRY`；输家不报错，**重读赢家的行、转为一次条件更新**——首建竞态的终点恒为一行，而不是 5xx。
    
*   **事件与迁移进同一事务。** `followup.opened` / `followup.closed` 不做 `catch {}` 吞异常——事件流是"她办完了几件"的唯一依据，静默丢一条就等于统计失真。
    

两处写入保护：

*   灰度两闸不在 metadata 里（§7.2），通用 `upsert-metadata` 物理上够不到。metadata 侧 `keepProtectedSubtrees` 保护的键是 `taskLedger` / `aone` / `metricsExclude`，与卡点链路无关。
    
*   `POST /scene-group/followup-gray-config` 是灰度名单落库的唯一通道：单事务内锁群行 → 只写配置表两行（§7.2）。退役看板键的防写回由通用写入入口的 `stripRetiredBoardCardpoints` 负责（§9.4）。
    

**仍存在的问题**（按影响排序）：

| 问题 | 影响 |
| --- | --- |
| bypass 场景下 `actor` 默认为 `'system'` | 审计链路上分不清是谁写的 |
| `SceneGroupService.disband` 零 followup 清理 | 群解散后卡点仍留在表里（tm-console 侧注释声称 server 会处理，实际没有——**跨仓认知不一致**） |
| 流水线没有 test 阶段 | 不变量绊线只在有人手动跑时才生效（§15.2） |

## 14. 定向催办：卡点通知卡

产品口径三条：① 只通知锚定到具体真人的卡点；② 走钉钉**私聊表单卡**；③ 属首个触达里程碑（M1），前置于"看板健康度达标"那道门。

### 14.1 组成

| 文件 | 职责 |
| --- | --- |
| `src/service/followup/blockerNotifyCard.service.ts` | 发卡 + 四道闸 + 指纹去重 + 频控 + 账本 |
| `src/service/cardCallback/blockerNotifyHandler.ts` | 卡片回调（两个出口语义刻意不同） |
| `src/service/followup/followupTickService.ts` | 通知收敛遍 + `notifyDetail` 回执 |
| `src/controller/followup.ts` | `POST /api/v1/followup/notify`，`{"dryRun":true}` 只算不发 |
| `config.default.ts` | `followup.notify.{enabled,dailyCapPerPerson,excludeEmpIds}`，默认关 |

### 14.2 四条设计前提

*   **通知是对 open 集合的收敛遍，不是升格的副作用。** 升格有两条路（reflection turn 驱动 + 日批静默补位），挂在任何一条上另一条就漏，发卡失败也会永久丢。判据是「当前是 open ∧ 账本没推过」——重跑幂等、漏推自愈（实测第二次跑 `notified:0 / notifySuppressed:1`，不重发）。
    
*   **去重键是** `**sha1(群 + 规整标题)**` **指纹，不是 itemId。** itemId 带日期盐，同一件事隔天复提是新 id，按 itemId 去重会同一卡点天天推一张。
    
*   **账本落** `**project-event**`**（**`**followup.notified**`**），不落** `**item.payload**`**。** runtime 每轮 upsert 整体替换 payload，写那儿下一轮就被抹掉。
    
*   **幂等 = 原子占位 + 有界收尾。** 账本是全时段去重真值，但它**发完才写**；从发卡成功到账本落地之间那段窗口，第二次调用会看到"还没推过"而重发。所以发卡前先 `SET NX`（7 天 TTL）抢指纹，抢到才发；发卡失败就释放；**账本没落不释放**——靠占位继续挡下一轮。发卡成功之后的收尾（认领、上下文、账本、配额）整段**有界**：卡已经在用户手机上了，后面任何一步抛错都不能让账本与配额写不进去，失败只留 warn。缓存不可用时**降级放行并留痕**——拒发会把一次抖动放大成整批不推。这条不只防并发：单实例"收尾抛错 → 账本没落 → 下一轮重推"同样可复现。
    

### 14.3 四道闸（控制打扰面）

真人形状闸 `/^[A-Za-z]{0,4}\d{4,}$/`（外包工号算真人，群沙箱 `g_` 前缀被挡）→ `excludeEmpIds` 点名排除（真人形状的数字人工号，形状闸认不出，只能点名）→ 免打扰（`sendTemplateCard` 不过 DND 门禁，必须自行校验）→ 每人每天封顶 3 张（超出顺延并逐条 log，不静默截断）。实测 11 条候选中真人闸挡掉 4 条（等的是恩熙自己）。

### 14.4 卡片交互语义

*   **「我已知晓」只落** `**followup.acknowledged**`（带响应时延），**刻意不改状态、不推** `**lastActivityAt**`——否则反复点卡片就能给自己的卡点无限续期，催办当场失效。
    
*   **「卡点判断错误」落** `**followup.false_positive_feedback**` 并走 `transition false_positive`，补充框里的自由文本是改判定 prompt 的直接输入。
    
*   **提交与状态推进解耦。** 关闭只由语义判定完成，卡片提交不直接改真值状态，避免人工点击绕过证据闸门；web 对卡点永远只读。
    
*   **回调身份靠发卡时认领，不靠模板。** 共享模板的提交回调只回模板自己声明的键（`convId`、`kind='clarify_form'`、表单字段、robotCode），`itemId` / 指纹 / 标题**一个都不回来**。所以业务身份在发卡时按 `outTrackId` 存一份缓存，并向 `CardOwnerRegistry` **认领**这张卡——漏认领会被公共表单 handler 接走、置灰、且不报错。
    
*   `**dryRun**` **回执**带 `notifyDetail:[{itemId,empId,sent,reason}]`："会推给谁"由回执自答，不依赖服务端日志（否则"没真发"与"被闸挡了"在计数里不可区分）。注意 `dryRun` 只挡发卡那一步，时间规则照常执行并写库，它**不是整轮只读**——要预览就用只读的 list。
    

### 14.5 验证状态

灰度链路已端到端跑通，每段都有日志或库记录可查：

```plaintext
配置同步（syncOwner 自证，非 owner 环境无写权）
  → server 行级真值（配置表单源，两闸合取成立）
  → 旁听：收每条群消息 → 静默成段 → 投群沙箱
  → 语义判定 + 证据闸（引旧证据的关闭动作被正确拒绝）
  → 候选到点升格 open（日批 promoted:1）
  → 私聊发卡（免打扰 / 配额 / 指纹占位 / 账本 / 有界收尾，全程零 warn）
  → 卡片渲染（四行标题不裁 + 两选项 + 补充框）
  → 回调「我已知晓」→ followup.acknowledged 落库
```

其中两条关键不变量在真实数据上被验证过：

*   **时间闸靠一正一反两个观测点。** 到点前 tick 回 `promoted:0`（闸挡住），到点后回 `promoted:1 / notified:1`（闸放行）。只看后者证明不了阈值在工作——它可能压根不看时间就升格，所以反向对照不能省。
    
*   **「我已知晓」不给卡点续期。** 点击后真值仍是 `open`、计时锚点不动。这条不变量原先只写在注释里，现已被真实点击验证。
    

**待验证项**（不当成已验）：`false_positive` 分支在最近一轮链路里未重跑；真实对话产生 `new` 候选的样本仍然稀少（观测到的两次真实消息，一次被判为正常协作、一次命中已存在的 open，均符合 §6 的保守口径）；完整 12 工作小时的自然计时与 cron 自动车道尚未在真实时间尺度上走完一遍。

后续规划：持续累积判定质量样本、沉淀催办效果指标、扩容频控与收件人范围。

## 17. 设计演进与取舍

本节记录方向**被推翻过**的决策。它们比最终形态更能说明判断依据，也是这套系统里绝大多数"看起来多余"的机制的来源。

### 17.1 卡点表示：LLM 写 markdown → 结构化真值 + 只读投影

最初卡点是 LLM 往看板 markdown 里写的一段文本，前端正则解析。推翻的理由不是"不够优雅"，而是这条路径上**没有任何一个环节能承载状态与时间**：没有状态就无法区分"新提出"和"挂了三天"；没有时间就无法判"无响应"；没有责任人锚定就不敢催人；没有原文就无法回查。加了六态状态机与真值表之后，markdown 那一路连同 `BlockerEntry`、`SOLUTION_PLACEHOLDERS`、`SHOW_BLOCKERS_IN_PERSONAL_SUMMARY` 一并删除，不留兼容分支。

### 17.2 关闭对齐：字面相似度 → 模型自证

先做的是字面相似度判据（比较 item 的 `unblockAction` 与证据句）。**实测判据无效**：关错的 3 条相关度 0.010 / 0.023 / 0.054，关对的 12 条 0.000~0.375，分布完全重叠。原因是根本性的——请求语与交付语天然不共词，字面手段量不了语义对齐。于是改成要求模型显式输出 `satisfies`，把"凭什么"交回给唯一有语义能力的组件，代码只负责检查它有没有说、说的那句原文在不在窗口里。

留下的方法论是：**先想清楚一个判据在正负样本上的分布是否可分，再实现它。**

### 17.3 关闭出口：全部交给模型 → 四出口白名单

原实现允许模型下达任意 `FollowupStatus`，只靠迁移白名单兜底，破口在于 `expired` 与 `open` 恰好都是合法迁移目标（§4）。教训是：**"凡是代码能判的绝不交给便宜模型"必须在类型边界上强制，写在 prompt 里等于没写。**

### 17.4 候选期内被办完：静默丢弃 → 回收 + 事件留痕

原实现对 `candidate → resolved_*` 直接 `continue`。以为是边缘情况，实测是 **17/24 的主路径**，后果是候选一路挂到升格、5/5 假升格。改成 `discard` + `followup.resolved_as_candidate` 事件后，真值表只含真正成立过的卡点，而"她办完了几件"从事件流数。

**这一条同时改变了对"丢弃"的认识**：任何静默丢弃都会在别处变成假数据，所以计划层引入了 `skip` 动作类型——不落库，但必须可见。

### 17.5 窗口清洗：按 `hide` 标志 → 按标记

两种按 `hide` 的方案都试过并被数据否掉：全信 `hide` 漏 19.5%，凡 `hide` 就丢会误删 94 个装着真人发言的信封（§6.7）。最终按标记剥离，并接受"摘掉唯一的说话人标识可能少抽几条"这个代价——因为它的方向是漏报而不是乱报。

### 17.6 人工改判：保留 → 取消

早期设计里 `false_positive` 有人工复审兜底。产品拍板卡点不做人工关闭、只由恩熙判断之后，人工口取消。**这次取消直接抬高了代码闸的重要性**：它从"两道兜底之一"变成"唯一兜底"，这也是 §6.2 / §6.3 里所有口径一律往严的靠的直接原因。

### 17.7 静默群：接受不覆盖 → tm-console 日批

挂 reflection 的固有代价是静默群不跑时间规则。曾考虑在 runtime 侧加独立定时器，否掉的理由是 runtime 是按会话起的沙箱进程，没有"扫全量群"的位置。放到 tm-console 日批，代价是计时常量需要在两个仓各存一份镜像（§9.5），换来的是灰度数据源统一、且日批不需要任何模型调用。

### 17.8 灰度入口：脚本与手工改 metadata → 配置中心单一真值源

灰度最初靠脚本改群 metadata，旁听则走另一条路径级配置。双源的后果是一种很难发现的偏态：**群能被监听、但卡点链路把它过滤掉**（或者反过来），两侧日志都正常。收敛方式不是让 runtime 也去读配置中心（它读不到），而是让 server 在同一个事务里把两闸写成一致的一份，metadata 从此降格为投影。（这层镜像后来又整体退役，见 §17.14。）

同一次收敛还带出两条设计判断：多环境共用数据库时，**写库权必须由配置显式声明归属**，不能靠"两边内容保持一致"的纪律（§7.2）；reconcile 的**归属判据要尽可能窄**，否则爆炸半径会扩散到与卡点无关的群。

### 17.9 投影维护方：runtime → server

投影原先由 runtime 在写成功后整体重算，于是出现两个问题：日批升格不刷投影（静默群的升格要等下一次 runtime pass 才显示），以及"真值在 server、投影在 runtime"这种维护方分裂。收归 server 后，两条升格路径共用同一段重算逻辑，runtime 删掉自己那份实现。

代价是**部署顺序不能反**：server 必须先具备投影维护与嵌套保护能力，否则会出现一段"谁都不维护投影"的真空。（这一步仍保留了"投影落库"，最终连落库本身也被删掉，见 §17.13。）

### 17.10 计时绊线：断言当前值 → 断言产品口径

灰度观察期为了当场攒够时长，临时把 `openHours` 降到 1、把工作时段上界从 20 放宽到 21，而绊线用例**跟着改成断言临时值**——等于把调试值写成了规格，再没有任何东西会提醒回退。窗口一动，单日推进小时数从 10 变 11，所有跨天算例的到点时刻集体提前（10:00 提出的卡点，从次日 12:00 到点变成次日 11:00）。

现在的做法见 §9.5：绊线只断言产品口径，算例显式传 cfg，不跟默认值走。**临时调参必须留一条会变红的绊线**，否则它迟早变成规格。

### 17.11 并发正确性：靠调度错峰 → CAS

早期依赖"reflection 单飞 + 日批错峰"来避免并发写同一条卡点。这是事实规避而不是设计保证：两条升格路径本来就可能同时命中同一批群。改成 CAS 之后，撞车有了明确语义（409 → `conflict`），既不会后写覆盖先写，也不会为同一次迁移落两条事件；`conflict` 计数本身还成了"两条路径在抢同一批群"的观测口。

### 17.12 装配保障：靠单测 → 靠源码扫描绊线

灰度同步器是 singleton，却注入了 request 作用域的依赖，容器直接拒绝创建——它**从未启动过**（一行库都没写），并且同一 controller 名下的所有路由一起 500。而故障期间相关目录的**单测全绿**：手搓 service 的单测天然绕过依赖注入容器，测不到装配。

所以补的不是单测，而是一条**源码扫描绊线**：凡被这个 singleton 注入的类，自己必须是 app 作用域。这条经验可以推广为：**测试要守的是失效真正发生的那一层，不是最容易写的那一层。**

### 17.13 投影：写时落库重算 → 读时派生

§17.9 把投影收归 server 之后，形态仍是"写时重算 + 落库"：迁移事务内重算 open 全集、先取群行写锁、逐字比对跳过写入。这套机制运转正常，但复盘发现**问题出在"落库"这个形态本身**：只要投影持久化，就要保证每条写路径（upsert / transition / discard）都不忘重算，漏一条就漂移；还要永远防着旧版本 runtime 整包写把旧投影写回去（嵌套保护）。真正的解法是把持久化整个拿掉：`open-projections` 读时从真值表即时派生，写侧只剩真值与 CAS。**这次是删多于增**——重算函数、群行写锁、比对跳过全部不再需要，"投影与真值不一致"这个状态空间直接消失。教训：**派生物的终极收敛不是"维护它一致"，而是"不存它"。**

### 17.14 配置：配置表 + metadata 镜像 → 配置表单源

两闸原先由 server 单事务写成"配置表两行 + metadata 镜像"，runtime 与日批读 metadata。镜像的唯一作用是兼容旧读口，代价是要永远养着它：`keepProtectedSubtrees` 得护住这两个键（含嵌套、无首次写入例外），两个载体只要漂移一处，闸门就偏态。把所有读口改成群列表接口的行级配置输出后，镜像失去最后一个读者，随即退役——两闸**从 metadata 里物理移除**，通用整包写从此理论上够不到它们；metadata 的保护逻辑收窄回 `taskLedger` / `aone` / `metricsExclude` 这些与卡点无关的既有键。判据是：**镜像该不该删，不看"还有没有人写它"，看"还有没有人读它"。** 存量由 `backfillLegacyGroupConfigs` 迁移工具先行把 metadata 里的配置搬进表里，再摘镜像。

### 17.15 toolEvidence：保留工具证据段 → 整块删除

抽取窗口曾有一段 toolEvidence：把恩熙的工具调用与结果渲染进文本给模型看，还养了一套配套 fixture。最终整块删除（净 -833 行），两条依据都来自对真实数据的复盘：其一，这段信息是**冗余**的——窗口里的人际对话与恩熙正文已足够支撑判定，多塞工具细节只增加便宜模型的输出预算压力与误抽面；其二，它的 fixture 是**手写的，从未与真数据对过一次账**——用例长期全绿，是因为测试与实现在互相印证对方的假设，而不是在印证现实。教训：**不经真数据对账的 fixture 不是证据，是自证**；删一个模块之前先问"它最后一次被真实数据验证是什么时候"。

### 17.16 追问卡：正文隐没 → 语义占位

`ask_user_followup` 的正文按窗口约定不复述，但原先这让"恩熙追问了一张卡、对方还没填"在窗口里**彻底不可见**——而"问了问题等回复"恰恰是卡点最典型的出生形态。现做法是留一个语义占位（`VISIBLE_TOOL_PLACEHOLDER`）：只告诉模型"这里有一张等对方填的追问卡"，不复述内容；判据函数 `hasVisibleToolCall` 同时被旁听在场判定复用，"什么算恩熙发过声"只有一份口径。底线不变：占位只供语义理解，**不能作证据锚点**——抽取的证据闸只认真人原话。

### 17.17 离线工具：仓内 → 仓外

回放 harness 与评测 CSV 导出原先都是仓内 npm script，现全部移出（runtime `scripts/replay-followup.ts` 删除、tm-console 的 `evaluationCsv.ts` / `exportFollowupEvaluation.ts` 删除）。直接动因是 tm-console 的 Midway FaaS 构建没有 tsconfig include 白名单，仓内脚本会持续被编译进产物。移完之后的边界更干净：**仓内只留线上与离线共用的纯函数（**`**model.ts**` **/** `**planner.ts**`**），harness 全在仓外**，"回放结论 = 线上结论"靠纯函数签名这一处唯一耦合点维持（§2.3）。
