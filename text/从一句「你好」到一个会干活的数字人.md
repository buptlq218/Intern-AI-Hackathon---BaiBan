# 从一句「你好」到一个会干活的数字人

阿里内部已经有 Devix、AgentForce 等数字员工实践。随着用户使用习惯逐步向云端迁移，Aone Sandbox、身份权限体系以及 Skill、MCP 等基础设施不断成熟，构建和运行一个云端 Agent 的门槛正在快速降低。相比偏通用的数字员工，我们面对的是更具体的业务场景 - 恩熙正是在这样的技术条件和业务需求下诞生的。

## 二、一句“你好”如何走完整条链路

以个人钉钉会话为例：

> **用户：“你好” ->  tm-console监听 -> 转发沙箱数字人进程 ->  NC生成回复  -> 恩熙同学：“你好，有什么可以帮你？”**

![ChatGPT Image 2026年7月27日 20_29_50.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/9f0094ac-78c2-49c2-96e2-cc8f18eefb84.png)

1.  **tm-console 监听用户消息“你好”**
    
    我们通过钉钉SDK，与钉钉保持长连接，持续接收个人和群聊消息。
    
2.  **tm-console 反馈钉钉 “消息已收到” 并对消息进行预处理**。
    
    收到消息后，立即返回消息回执，避免钉钉因为等待超时而重复推送。随后解析文字、图片和文件：图片转存至 CDN，文件转存至 OSS；最后将消息内容、发送人、个人或群聊来源以及链路标识，组装成 Runtime 可以统一识别的结构化消息。
    
    ![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/9a0f4702-4670-4c47-968f-48a3e4e1bcfe.png)
    
3.  **判断消息所属工作空间**
    
    tm-console 会先区分当前是预发还是线上环境，再判断消息来自个人会话还是群聊：
    
    *   个人消息以本人工号作为路由 ID，进入本人的 Sandbox。
        
    *   群消息根据钉钉群 ID 生成稳定的 g\_xxx 路由 ID，进入该群独立的 Sandbox。
        
    *   预发和线上分别维护自己的 Sandbox，不会相互串用。
        
4.  **找到并准备对应的 Sandbox**
    
    *   如果 Sandbox 存在并且仍处于 Running 状态，就直接复用，同时为它续期。
        
    
    *   如果 Sandbox 不存在、已经失效或者无法访问，就清理旧的路由记录，重新创建一个 Sandbox。
        
    *   为了避免多条消息同时创建多个 Sandbox，创建前会先获取一个**分布式锁**。
        
    *   新 Sandbox 创建时会挂载该用户或群对应的 Volume，注入环境配置，启动 Runtime，并等待健康检查通过。
        
5.  **把“你好”交给 Runtime**
    
    Sandbox 准备完成后，tm-console 通过 Aone Sandbox SDK 的命令执行能力，在 Sandbox 内执行：
    
    ```shell
    //  前面整理好的结构化消息会作为请求体一起发送给 Runtime。
    
    curl -X POST http://localhost:3000/message \
      -H "Content-Type: application/json" \
      -d '{"text": "Hello"}'
    ```
    
6.  **Runtime 生成回答**
    
    Runtime 找到对应会话，调用模型和 Skills 处理“你好”，逐步生成“你好，有什么可以帮你？”。
    
7.  **把回答变成钉钉卡片**
    

Runtime 通过一个内部 HTTP 客户端调用 tm-console 的钉钉回复服务；tm-console 再负责创建或持续更新钉钉 AI Card。最终用户在原会话里看到完整回答。

## 三、数字人 tm-cosnole 接入层与沙箱运行底座

![ChatGPT Image 2026年7月28日 12_03_03 (1).png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/b7523208-5369-4f54-8ac0-76697908b961.png)

我的工作位于产品入口和 Runtime 大脑之间：让消息送得到、环境起得来、身份用得对，并且整条链路能够被观测。

### 1. 消息链路控制：消息送得到，问题查得清

![ChatGPT Image 2026年7月28日 12_03_04 (2).png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/84faf966-89f9-4c17-92da-1e75ea4ce7f4.png)

#### 链路控制

```text
接收消息 → 去重和整理 → 选择个人/群 Sandbox → 准备环境 → 投递 Runtime → 更新用户卡片
```

*   多台 tm-console 同时收到同一事件时，由 Tair 保证只有一台继续处理。
    
*   图片和文件在钉钉下载凭证过期前转存；群消息保留真实发送人和增量上下文。
    
*   冷启动时先展示“正在准备环境”，环境就绪后继续更新同一张卡片。
    

#### 日志与业务监控

每一轮钉钉消息在入口生成一个 `routeId`，随后带着它经过 Sandbox 准备、Runtime 投递、Runtime 回调和钉钉发卡。日志统一进入 SLS，看板可以从整体指标下钻到一轮消息的具体阶段。

```text
平均首响耗时｜首响 P90｜冷启动首响 P90｜首响成功率 / 无响应轮次

```

这里的“首响”是第一条 AI Card 成功推送；“P90”表示 90% 的请求能在这个时间内完成首响。

#### 冷启动优化

即将上线的热资源池把最耗时的 Sandbox 创建和 Runtime 启动提前到后台：

```text
原链路：用户发消息 → 创建 Sandbox → 启动 Runtime → 健康检查 → 投递
资源池：后台准备 Running Sandbox → 用户发消息 → 领取并绑定 → 健康检查 → 投递

```

资源池维持少量空闲实例，领取失败时仍回到标准创建链路，不牺牲可用性。当前 Aone Volume 只能在创建 Sandbox 时挂载，因此启用 Volume 的身份仍会跳过资源池；两者同时命中是下一步需要补齐的能力。

### 2. Sandbox 运行底座：实例可以重建，工作不能丢

![ChatGPT Image 2026年7月28日 12_03_05 (3).png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/f5cda62a-4e5d-48b7-a366-641033e41969.png)

#### 环境与生命周期

```text
模板镜像 → 注入用户/群、业务域和 Runtime 版本 → 挂载 Volume
        → 启动 Runtime → /health 通过 → 写入路由 → 开始接消息

```

*   \*\*已有且可用：\*\*直接复用并续期。
    
*   \*\*不存在：\*\*获取分布式锁，只创建一个新 Sandbox。
    
*   \*\*已经失效：\*\*摘掉旧路由并重建，再挂载原来的 Volume。
    

#### 数据放在哪里

```text
Volume：保存 /root/instances 下的状态、记忆和会话，Sandbox 重建后重新挂载
OSS：保存钉钉文件、消息历史等业务数据，不承担 Sandbox 磁盘快照恢复
MySQL：记录当前 Sandbox、Runtime 版本、心跳和身份绑定
Tair：负责创建锁、消息去重和短期映射

```

#### Runtime 版本怎么更新

tm-console 下发目标版本后，Sandbox 内的升级进程从 CDN 下载新 Runtime；等当前任务空闲，再原子切换 `current` 软链接并重启进程。Supervisor 负责把 Runtime 重新拉起。

```text
下发版本 → 下载到新目录 → 等待空闲 → 切换 current
        → Supervisor 重启 → Runtime 立即心跳 → tm-console 确认升级成功

```

Runtime 启动时立即上报一次心跳，之后每 5 分钟上报版本、进程、启动时间和忙闲状态。tm-console 用它掌握 Runtime 的运行状态，并确认动态升级是否真正生效；请求进入业务路由前，仍以 `/health` 检查为准。

### 3. Agent 身份控制：AuthX、Git、a1 各自讲清楚

![ChatGPT Image 2026年7月28日 12_03_06 (4).png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/Mp7ld75zjvXRpOBQ/img/203e6e23-81be-42dc-89e3-267b016a2371.png)

| **能力** | **当前使用谁的身份** | **怎么实现** |
| --- | --- | --- |
| AuthX 兼容的 CLI / HTTP 服务 | 个人为本人；群为已确认的技术负责人，同时携带 Agent 和 Sandbox 身份 | Aone Egress 为出站请求注入短期身份证明，下游按原有权限继续鉴权 |
| Git commit / push | 优先使用当前这轮消息真实发送人的代码身份 | Git Proxy 只在当前进程内设置提交人和访问凭据，不修改仓库 remote，也不把个人凭据写进仓库 |
| a1 | 当前使用 Runtime 初始化时配置的恩熙账号，不随每轮消息发送人或群技术负责人变化 | Runtime 启动后安装 a1，并使用预置代码平台身份完成登录；Sandbox 重建后重新初始化 |

这三条身份链路目前互不自动同步。AuthX 为 MW、Normandy、maxc 等工具和服务提供统一身份底座，但每个调用方和资源端仍需要实际支持 AuthX；a1、Git 不会因为 Sandbox 绑定了 AuthX 就自动切换身份。

AuthX 的核心表达是：

```text
谁授权（User） + 哪个 Agent 在执行（Agent） + 哪个 Sandbox 在承载（Sandbox）

```

个人 Sandbox 默认绑定本人；群 Sandbox 绑定技术负责人。切换群技术负责人时，目标负责人必须本人通过 BUC 确认，身份变化后冷建新 Sandbox，并以在线探测结果确认三层身份真正生效。AuthX 只证明身份，不增加 ODPS、SLS、MW 等资源权限。
