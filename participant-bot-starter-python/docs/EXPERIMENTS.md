# 现场待验证清单

技术编程细则里有些地方没写清，或者写了但**必须用真实引擎确认**。这些不确定性直接
影响策略，所以按「影响大小 × 验证成本」排了序。

验证方法统一是：**跑一局训练赛 → `python3 tools/analyze.py runtime/` → 看报表的
「现场实验证据」一节**。每条实验都写清「看什么字段能判定」。

> ⚠️ 别用 `runs/*.jsonl` 那条路径 —— 那是备用独立 runner 的产物。正式赛跑的官方
> `bot.py` 落在 `runtime/matches/<matchCode-matchId>/`，格式是原始帧转储，
> 由 `tools/capture.py` 重建成碰撞事件。**E1 / E2 / E5 / E12 现在是报表里的
> 自动输出**，不用再人肉数帧。

## P0：会改变策略结构的（开场 15 分钟内必须验完）

### E1 —— 场地边缘接触算不算「障碍物碰撞」？

**为什么重要**：细则说边缘会「强制拉回可行驶区，不会落水」，但没说这次接触
①是否扣 1 果实、②是否重置无碰撞计时。三种可能，策略完全不同：

| 情况 | 含义 | 策略 |
|---|---|---|
| 不扣分 + 重置计时 | **免费的保活手段** | 保活兜底一律去贴边，不撞石头。这是白捡的 2 分/30s |
| 扣分 + 重置计时 | 等价于障碍物 | 保持现状（撞最近障碍） |
| 不扣分 + 不重置计时 | 边缘是纯粹的中性墙 | 贴边安全但不能用来保活；避战时可以贴边躲 |

**怎么验**：开局把车往边上开，撞上后看 replay：
- `score_delta == -1` → 扣分
- 之后 `seconds_since_self_collision` 是否归零 → 是否重置计时

**代码位置**：`firefly/constants.py` 的 `RULE_BORDER_IS_OBSTACLE_UNKNOWN`；
如果确认是「免费保活」，改 `firefly/strategy.py::_cheapest_interaction`，
把 `idle_hit_obstacle` 的目标从最近障碍点换成最近边缘点。

### E2 —— 无碰撞计时的起点是「开局」还是「上次碰撞」？是否严格 30s？

**为什么重要**：`idle_seek_at=20` 这个参数完全依赖它。如果实际是从开局算起且
第一次惩罚在 30s 整，那我们必须在 25s 前完成第一次碰撞。

**怎么验**：开局故意不碰任何东西，看 `score` 在第几秒掉 3。

**代码位置**：`Tune.idle_seek_at` / `idle_obstacle_fallback_at`。

---

### ~~E3 —— `turnLeft` 让 `angle` 变大还是变小？~~ ✅ 已确认

**结论（赛前，读官方 starter 源码）**：官方基准策略用
`turnRight if delta > 0 else turnLeft`（`delta = 目标角 - 当前角`），
即「要把 angle 调大就右转」→ **`turnLeft` 使 `angle` 减小**。

已落地：`TurnCalibration.sign` 默认 -1，并保留在线标定以防版本差异。
`test_strategy.py` 里有一条用例专门钉住这个方向（目标在左上方必须 `turnLeft`）。

---

### ~~E4 —— 我方精灵 id 怎么拿？~~ ✅ 已确认

**结论**：`rabbits[].id == str(botId)`，本地 sample 服务会加 `ai:` 前缀。
官方基准和我们的 `_resolve_self_id` 都同时兼容两种。`botId` 由 `botConnected` 下发。

**仍要在现场确认**：`analyze.py` 输出里「我方碰撞」不为 0。如果全程 0 碰撞，
先查是不是 id 没认上。

---

### E12 —— 本地时钟与服务端时间是否对得上？ 🆕

**为什么重要**：官方 `refreshData.data` **没有** `elapsedSeconds` / `remainingTime`，
所以我们用本地单调时钟（`on_start_game` 对零）推算两个 30s 周期。如果 `startGame`
与第一帧之间有明显延迟，或帧流有卡顿，相位会漂。

**已有对策**：能量重置会被观测到（能量上涨 → 重新校正相位），所以能量周期是自纠的。
但**无碰撞惩罚周期没有可观测的锚点**，只能靠本地时钟。

**怎么验**：看 replay 里 -3 果实发生的时刻，和我们日志里 `idle_for` 的读数是否吻合。
若差异大于 2 秒，把 `Tune.idle_seek_at` 调更保守（例如 18）。

## P1：会影响调参但不改结构

### E5 —— 对手攻击力能否稳定从能量跌幅反推？

**为什么重要**：这是本方案最大的信息优势（`worldmodel._diff_sprites`）。

**风险**：如果能量字段有延迟、或碰撞与能量重置同帧发生，推断会出错。

**怎么验**：`analyze.py` 的「对手出价」一节。如果对手出价看起来是干净的整数
（如 50 / 200 / 500），说明推断有效。如果全是零散小数或空，说明这条路不通，
需要退回固定竞价档位。

---

### E6 —— 森林之心生成时间是否真在 30/90/150s？

细则说「通常在第 30、90、150 秒附近生成，并会在生成前约 5 秒进行画面提示」，
但也明确要求「以实时字段为准」。

**怎么验**：记录 `goldCarrot` 从 `{}` 变成有坐标的时刻。

**用途**：如果稳定，可以提前 3~5 秒往地图中心预定位，抢心成功率会明显提高。
**注意**：不要改成只信本地计时器，细则明确反对。

---

### E7 —— 三车连撞的结算顺序

细则说按「汽车追尾原则」两两判定，但没给顺序。

**怎么验**：在 replay 里找同一时间窗口内的多条 `collision` 记录。

**用途**：如果发现「后撞上来的一方吃亏/占便宜」有规律，可以据此决定要不要主动
往两车缠斗里插一脚。

---

### E8 —— 碰撞冷却是否严格 1.5s、是否按「对」计算

**怎么验**：看同一对手连续两次 `collision` 的时间差最小值。

**用途**：影响持森林之心时的目标轮换策略（10s 内最多能打几个人）。

## P2：有余力才做

### E9 —— 反弹公式的实际系数是否与细则一致
用 `collision` 前后两帧的 `velocity` 反解，验证 `0.02 / -0.3 / 0.7`。
影响短期轨迹预测精度。

### E10 —— 撞击持心者时我方是否也进入更强反弹
细则说「增益精灵撞击对手时，对手的反弹效果会更强（约 1.5 倍）」。
影响逃离持心者的路线规划。

### E11 —— 果实降到 0 的精灵是否立刻从 `rabbits` 消失
影响 `rivals` 的过滤逻辑（现在靠 `active` 和 `score > 0` 双重判断）。

```
### E1 结论（14:35，训练赛 forest-xxx）
边缘接触：score_delta = 0，且 idle 计时**没有**归零。
→ 属于第三种情况：中性墙。保活仍需撞真障碍物；但避战时可以放心贴边。

```
